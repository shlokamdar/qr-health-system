# Chapter 4: System Design Details
**Project Title**: PulseID - QR-Based Unified Health Record System

## SECTION A: DATA LAYER & DATABASE

### A1. Database Schema Details

**1. All Database Tables**
The system uses Django’s ORM and connects to a default SQLite3 database (though designed for PostgreSQL). Essential tables include:
- `accounts_user` (Custom User extending AbstractUser)
- `accounts_notification`
- `patients_patient`
- `patients_emergencycontact`
- `patients_patientdocument`
- `patients_oldprescription`
- `patients_sharingpermission`
- `patients_otprequest`
- `doctors_hospital`
- `doctors_department`
- `doctors_hospitaladmin`
- `doctors_doctor`
- `doctors_consultation`
- `doctors_appointment`
- `labs_diagnosticlab`
- `labs_labtechnician`
- `labs_labtest`
- `labs_labreport`
- `records_medicalrecord`
- `audit_accesslog`
- `support_supportticket`

**2. Each Table's Complete Structure (Key Examples)**

**`accounts_user`**
- `id` (PK, Integer, NOT NULL)
- `password` (String, NOT NULL)
- `last_login` (Datetime)
- `username` (String, NOT NULL, UNIQUE)
- `email` (String, NOT NULL, UNIQUE)
- `role` (String, Choices: PATIENT, DOCTOR, LAB_TECH, HOSPITAL_ADMIN, ADMIN, Default: PATIENT)

**`patients_patient`**
- `id` (PK, Integer, NOT NULL)
- `user_id` (FK to `accounts_user`, UNIQUE, NOT NULL - 1:1 Relationship)
- `health_id` (String(50), UNIQUE, NOT NULL)
- `qr_code` (ImageField, Nullable)
- `date_of_birth` (Date, Nullable)
- `contact_number` (String(15))
- `address` (Text)
- `blood_group` (String(5), Choices: A+, A-, B+, B-, AB+, AB-, O+, O-)
- `allergies` (Text)
- `chronic_conditions` (Text)
- `gender` (String(10), Choices: Male, Female, Other, Default: Male)
- `created_at` (Datetime, auto_now_add)
- `updated_at` (Datetime, auto_now)

**`patients_otprequest`**
- `id` (PK, Integer, NOT NULL)
- `doctor_id` (FK to `doctors_doctor`)
- `patient_id` (FK to `patients_patient`)
- `otp_code` (String(6), NOT NULL)
- `is_verified` (Boolean, Default: False)
- `attempts` (Integer, Default: 0)
- `is_revoked` (Boolean, Default: False)
- `delivery_method` (String(20), Choices: SMS, EMAIL, DASHBOARD, Default: DASHBOARD)
- `verifier_type` (String(20), Choices: PATIENT, EMERGENCY_CONTACT)
- `created_at` (Datetime, auto_now_add)

**3. Relationships**
- **One-to-One:** `accounts_user` has a 1:1 with `patients_patient`, `doctors_doctor`, `doctors_hospitaladmin`, `labs_labtechnician`.
- **One-to-Many (1:N):** `doctors_hospital` to `doctors_department`. `patients_patient` to `patients_patientdocument`, `patients_oldprescription`, `patients_sharingpermission`, `records_medicalrecord`, `doctors_consultation`, `doctors_appointment`.
- **Cascade Deletion:** Maintained across most User-centric data. If a User is deleted, their associated Profile (`Patient`/`Doctor`) is deleted (CASCADE).

**4. Database-Specific Details**
- Features used: `JSONField` for `medicines` array in `patients_oldprescription` and `Consultation` and `result_data` in `LabReport`.
- Uses UUID4-hex hashing for Health ID generation algorithm: `f"HID-{uuid.uuid4().hex[:8].upper()}"`.

### A2. Data Types & Constraints
**1. Validation Rules**
- Health ID Format: `HID-XXXXXXXX` (where X is an 8-character uppercase hex string derived from UUID4).
- OTP Code Length: 6 characters. Attempt limits apply.
- Email: Must be unique across all roles.

**2. File Storage**
- QR codes: `qr_codes/` (saved as PNG, derived from html2canvas + Pillow).
- Doctor verification docs: `doctor_documents/licenses/`, `doctor_documents/degrees/`, `doctor_documents/ids/`
- Medical documents/reports: `patient_documents/`, `old_prescriptions/`, `records/`, `lab_reports/`.

### A3. Authentication & Access Control
- **JWT Implementation:** `rest_framework_simplejwt`. Access Token lifetime is 60 minutes. Refresh Token lifetime is 1 day.
- **Roles & Permissions:** 
  - `PATIENT`: Can manage their own profile, grant/revoke sharing permissions (QR_QUICK or OTP_FULL), view/download their medical records.
  - `DOCTOR`: Must be "Verified" by System Admin. Authorization Levels: BASIC, STANDARD, FULL. Needs permission (OTP or QR scan) to access patient records. Can upload consultations and medical records.
  - `LAB_TECH`: Must belong to a DiagnosticLab. Uploads test data.
  - `HOSPITAL_ADMIN`: Manages specific hospital doctors and departments.
  - `ADMIN`: Overarching superadmin; verifies doctors, hospitals, labs. Enacts system restrictions and resolves tickets.

## SECTION B: BACKEND ARCHITECTURE

### B1. Django Project Structure
- **Apps:** `accounts`, `patients`, `records`, `audit`, `doctors`, `labs`, `support`, `utils`.
- **Models:** Built using `django.db.models`. Includes `AbstractUser` overriding, text choices for Enums, and automatic signal handling inside `save()` methods (e.g., QR generation).

### B2. Core Features Implementation
- **Health ID & QR Generation:** Auto-generated on `Patient` model save if empty. QR Code is a generated PNG with error correction level L, encoding the frontend landing URL (`/patients/{health_id}`).
- **Patient Record Access:** 
  - `AccessType.QR_QUICK` (24hr expiry, read-only preview). 
  - `AccessType.OTP_FULL` (Permanent until revoked, allows full view and adding records).
  - Doctors initiate an OTP request, which goes to `OTPRequest` model. Patients verify the OTP from the Dashboard.
- **Audit Logging:** Every major data transmission is tracked using `audit.models.AccessLog` identifying the `actor`, `patient`, `action` (e.g. VIEW_PROFILE, VIEW_RECORDS, LOGIN), `details` and IP Address.

### B3. API Details
- Configured using DRF ViewSets, APIViews, and routers under `/api/*`.
- **Auth:** 
  - `/api/auth/register/` (Registers new user)
  - `/api/auth/login/` (JWT Obtain Pair)
  - `/api/auth/refresh/`
- **Patient:** `/api/patients/`, `/api/patients/otp/request/`, `/api/patients/otp/verify/`, `/api/patients/{health_id}/` (public endpoint to scan QR).
- **Audit/Admin:** `/api/admin/stats/`, `/api/admin/doctors/{id}/manage/` (approval endpoints).

### B4. Error Handling & Validation
- Default DRF validation errors `{ "field": ["error message"] }`.
- Return HTTP Status codes: `200 OK`, `201 Created`, `400 Bad Request` (Validation issue), `401 Unauthorized` (Token expiry), `403 Forbidden` (Role restriction), `404 Not Found`.

## SECTION C: FRONTEND ARCHITECTURE

### C1. React Project Structure
- **Tech Stack:** React 18, Vite, React Router v6, TailwindCSS v4, Axios.
- **Components Hierarchy:** Placed inside `frontend/src/` with `pages`, `components`, `services`, `context`.
- **State Management:** Context API (`AuthContext.tsx/jsx`) used for authentication status, generic states via `useState` and `useEffect`.
- **API Integration:** Axios instances setup using base `API_URL`. Tokens are injected securely in request headers.

### C2. UI/UX Components & Screens
- **Routes:** 
  - Shared: `/login`, `/register`, `/forgot-password`, `/reset-password/:token`, `/patients/:healthId` (Public Patient View).
  - Patient: `/patient/dashboard`
  - Doctor: `/doctor/dashboard`
  - System Admin: `/admin-dashboard`, `/system/login` 

### C3. Design System
- **Colors & Tokens:** Strictly governed by `system_colours_and_design.md`. 
  - Primary Background: `#F8FAFB`
  - Cards: `#FFFFFF`
  - Primary (Sky Blue): `#3B9EE2`
  - Secondary (Mint): `#2EC4A9`
- **Typography:** `Inter` font.
- **Icons:** Solely `lucide-react`. No Emojis.
- **Health ID Card Canvas:** Fixed layout using dark background (`#0D1B2A`), generates downloadable 1200x750px PNG via `html2canvas`.

## SECTION D: SECURITY & COMPLIANCE

### D1. Data Security
- **Encryption:** Passwords hashed with PBKDF2 (Django standard).
- **Access Control:** Role-Based Access Control implemented via DRF Permission Classes. Cross-tenant isolation ensures Doctors cannot view random Patients without explicit `SharingPermission` or valid `OTPRequest`.
- **Session:** JWT stateless session handling, prevents server-side memory saturation.

### D2. Compliance
- **HIPAA-Inspired Audit Trail:** Real-time logging of access (`AccessLog` model). Read/Write activities mapped natively. It provides high traceability determining exactly who accessed what and when.

## SECTION E: DEPLOYMENT & INFRASTRUCTURE

### E1. Hosting & Deployment
- Database: Built for SQLite local development, but easily migrates to PostgreSQL for production environments via Django database config mappings.
- Environment Management: `python-decouple` used for secrets and keys logic (`.env`).
- Frontend configures CORS natively allowing specific Vite Dev Servers (localhost:5173/5174).

### E2. Performance Optimization
- Native TailwindCSS purging and JIT building. 
- DRF Pagination applied to view queries where responses list larger sets of Consultations or Prescriptions to manage SQL loads.
- Native throttling is defined inside DRF settings (`anon` config to 100/day, `user` config to 1000/day, `uploads` throttled to 20/day) preventing rate limit abuse.

## SECTION F: ADDITIONAL FEATURES
- **Notifications:** Base `Notification` model handles cross-platform broadcast alerts. 
- **In-App Messaging/Ticketing:** The `support.SupportTicket` model acts as a mechanism for end-patients and doctors to query SysAdmins (tracked as OPEN, IN_PROGRESS, RESOLVED, CLOSED).
- **Roles Aggregation:** Single `User` model encapsulates diverse portals without duplicate tables (Unified auth strategy).
